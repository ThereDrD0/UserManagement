## POST /api/users

**Позитивные**
Общая схема:
1. Приходит валидный запрос
2. Сервер создает пользователя
3. Пользователь реально создался
4. Пользователь имеет CountryIsoCode в верхнем регистре
5. Сервер возвращает 201 Created
6. Проверка контракта ответа:
   - Заголовок `Location` содержит валидный URI ресурса (`/api/users/{id}`)
   - Тело ответа десериализуется в `User`: `UserId != Guid.Empty`, `CountryIsoCode` в UPPERCASE, `DateCreated` в UTC (разница с UtcNow <= 5 сек), `DateModified == null`

Тест-кейсы:
1. Полностью валидный сценарий.
   - [ ] Locale = "ru-RU", CountryIsoCode = "RU"
2. Сервер принимает CountryIsoCode в верхнем, нижнем и смешанном регистре.
   - [ ] CountryIsoCode = "RU"
   - [ ] CountryIsoCode = "ru"
   - [ ] CountryIsoCode = "rU"
   - [ ] CountryIsoCode = "Ru"
3. Игнорирование лишних полей в JSON (клиентские id/даты игнорируются, генерируются сервером):
   - [ ] Тело запроса содержит клиентский id, dateCreated, dateModified или лишние поля -> поля игнорируются, сервер генерирует собственный UserId != Guid.Empty, DateCreated в UTC, DateModified == null

**Негативные**
Общая схема:
1. Приходит невалидный запрос
2. Возвращается ошибка валидации
3. Ошибка валидации содержит ошибку ровно с тем параметром, который был передан неправильно
4. Пользователь не был сохранен в репозиторий(и соответственно создан)

Тест-кейсы:
1. Locale не проходит валидацию, CountryIsoCode проходит
   - [ ] Locale = null - отсутствие значения (null)
   - [ ] Locale = "11-11" - цифры
   - [ ] Locale = "ru-ru" - вторая часть в нижнем регистра
   - [ ] Locale = "RU-RU" - первая часть в верхнем регистре
   - [ ] Locale = "rU-rU" - смешанный регистр, первая и вторая часть в неправильном регистре
   - [ ] Locale = "ыы-ЫЫ" - нелатинские буквы (кириллица)
   - [ ] Locale = "ru-RURU" - выше верхней границы лимита
   - [ ] Locale = "ru" - ниже нижней границы лимита
   - [ ] Locale = "ru_RU" - разделитель подчеркивание "_" вместо дефиса
   - [ ] Locale = "ru|RU" - другой символ вместо тире
   - [ ] Locale = "ruRU" - нет разделительного символа(тире)
   - [ ] Locale = "ru-RU\n" - спец. символы
   - [ ] Locale = "" - пустая строка
   - [ ] Locale = " " - пробел
   - [ ] Locale = "r-RU" - длина первой части 1 символ (ниже лимита 2)
   - [ ] Locale = "rus-RU" - длина первой части 3 символа (выше лимита 2)
   - [ ] Locale = "ru-R" - длина второй части 1 символ (ниже лимита 2)
   - [ ] Locale = "ru-RUS" - длина второй части 3 символа (выше лимита 2)
2. Locale проходит валидацию, CountryIsoCode не проходит
   - [ ] CountryIsoCode = null - отсутствие значения (null)
   - [ ] CountryIsoCode = "11" - цифры
   - [ ] CountryIsoCode = "ыы" - нелатинские символы (кириллица)
   - [ ] CountryIsoCode = "rrr" - выше верхней границы лимита
   - [ ] CountryIsoCode = "r" - ниже нижней границы лимита (длина 1 при минимуме 2)
   - [ ] CountryIsoCode = "RU\n" - спец. символы
   - [ ] CountryIsoCode = "" - пустая строка
   - [ ] CountryIsoCode = " " - пробел
   - [ ] CountryIsoCode = " RU" - пробел в начале
   - [ ] CountryIsoCode = "RU " - пробел в конце
   - [ ] CountryIsoCode = "R1" - буква и цифра
   - [ ] CountryIsoCode = "1R" - цифра и буква
3. Оба поля не проходят валидацию (400 Bad Request):
   - [ ] CountryIsoCode = "1", Locale = "invalid" - возвращаются ошибки валидации по обоим полям
   - [ ] CountryIsoCode = "", Locale = "" - оба поля пустые строки

## GET /api/users/{id}

**Позитивные**
Общая схема:
1. Приходит валидный запрос с существующим id
2. Сервер находит пользователя в базе
3. Сервер возвращает 200 OK
4. Проверяется соответствие полей (UserId, CountryIsoCode, Locale, DateCreated, DateModified)

Тест-кейсы:
1. Запрос с существующим валидным Guid:
   - [ ] id = существующий валидный Guid
   - [ ] id с шестнадцатеричными символами в верхнем регистре -> 200 OK

**Негативные**
Общая схема:
1. Приходит запрос с невалидным или несуществующим id
2. Сервер валидирует id (если невалидный - 400 Bad Request с описанием ошибки)
3. При валидном id сервер ищет пользователя в базе (если не найден - 404 Not Found)
4. База данных не модифицируется

Тест-кейсы:
1. id не является валидным GUID (400 Bad Request):
   - [ ] id = "00000000-0000-0000-0000-000000000000" - Guid.Empty
   - [ ] id = "not-a-guid" - случайная строка
   - [ ] id = "12345" - просто цифры
   - [ ] id = "12345678-1234-1234-1234-12345678901z" - буква среди символов
   - [ ] id = "12345678-1234-1234-1234-12345678901!" - спецсимвол ! на конце
   - [ ] id = "12345678-1234-1234-1234-1234567890123" - превышает макс длину
   - [ ] id = "12345678-1234-1234-1234" - длина меньше нужного
   - [ ] id = " " - пробел
2. id валиден, но пользователя нет в базе (404 Not Found):
   - [ ] id = несуществующий сгенерированный Guid

## PUT /api/users/{id}

**Позитивные**
Общая схема:
1. Приходит валидный запрос на обновление существующего пользователя
2. Сервер валидирует DTO и id
3. Сервер находит пользователя в базе
4. Сервер обновляет CountryIsoCode, Locale. DateCreated и UserId не меняются, DateModified выставляется в UTC и проверяется, что DateModified >= DateCreated
5. Сервер сохраняет изменения в репозиторий
6. Сервер возвращает 200 OK с обновленными данными

## GET /api/users

**Позитивные**
Общая схема:
1. Приходит запрос на получение списка всех пользователей
2. Сервер извлекает пользователей из хранилища
3. Сервер возвращает 200 OK со списком всех сохраненных сущностей с сортировкой (например, по UserId / DateCreated)

Тест-кейсы:
1. Получение списка при пустом хранилище (возвращается 200 OK и пустой массив []).
   - [ ] Хранилище пустое -> возвращается 200 OK и []
2. Получение списка при наличии нескольких пользователей (возвращается 200 OK, массив содержит всех созданных пользователей с точным совпадением свойств).
   - [ ] В хранилище несколько пользователей -> возвращается 200 OK со всеми пользователями
3. Получение списка с корректными параметрами пагинации (page, pageSize) с сортировкой (например, по UserId / DateCreated):
   - [ ] page = 1, pageSize = 2 при 5 пользователях - возвращаются первые 2 записи
   - [ ] page = 2, pageSize = 2 при 5 пользователях - возвращаются 3я и 4я записи
   - [ ] page = 3, pageSize = 2 при 5 пользователях - возвращается 5я запись
   - [ ] page = 4, pageSize = 2 при 5 пользователях - возвращается пустой список
   - [ ] page = 1 (без pageSize) -> возвращаются первые 10 записей (дефолтный pageSize = 10)
   - [ ] pageSize = 2 (без page) -> возвращаются первые 2 записи (дефолтный page = 1)
   - [ ] page = null, pageSize = null при 12 пользователях -> возвращаются все 12 записей (полный список без пагинации)
   - [ ] pageSize = 3 (без page) при 5 пользователях -> возвращаются 3 записи (дефолтный page = 1)
   - [ ] pageSize = 5 (без page) при 3 пользователях -> возвращаются 3 записи

**Негативные**
Общая схема:
1. Переданы невалидные query-параметры пагинации
2. Сервер строго возвращает 400 Bad Request с описанием ошибки валидации параметров пагинации

Тест-кейсы:
1. Невалидные значения page и pageSize (граничные page <= 0, pageSize <= 0 и нечисловые значения):
   - [ ] page = 0, pageSize = 10 -> 400 Bad Request
   - [ ] page = -1, pageSize = 10 -> 400 Bad Request
   - [ ] page = 1, pageSize = 0 -> 400 Bad Request
   - [ ] page = 1, pageSize = -5 -> 400 Bad Request
   - [ ] page = 0, pageSize = 2 -> 400 Bad Request
   - [ ] page = -1, pageSize = 5 -> 400 Bad Request
   - [ ] page = 0 -> 400 Bad Request (page <= 0)
   - [ ] pageSize = 0 -> 400 Bad Request (pageSize <= 0)
   - [ ] page = -1 -> 400 Bad Request (page <= 0)
   - [ ] pageSize = -5 -> 400 Bad Request (pageSize <= 0)
   - [ ] page = "abc", pageSize = 10 (нечисловое значение) -> 400 Bad Request
   - [ ] page = 1, pageSize = "xyz" (нечисловое значение) -> 400 Bad Request
   - [ ] page = "abc", pageSize = 2 -> 400 Bad Request
   - [ ] page = 1, pageSize = "abc" -> 400 Bad Request

## End-to-End

**Позитивный**
Общая схема:
1. POST /api/users создает пользователя (201 Created), запоминаем id, DateCreated
2. GET /api/users/{id} получает созданного пользователя (200 OK), сверяем поля
3. PUT /api/users/{id} обновляет пользователя новыми данными (200 OK), проверяем DateModified != null и DateModified >= DateCreated
4. GET /api/users/{id} повторно запрашивает пользователя (200 OK), проверяем сохранение изменений в хранилище
5. GET /api/users проверяет, что обновленный пользователь отображается в общем списке

Тест-кейсы:
1. Полный жизненный цикл пользователя:
   - [ ] Полный цикл: POST (ru-RU, RU) -> GET {id} -> PUT (en-US, US) -> GET {id} -> GET all

## Тестирование потокобезопасности хранилища (InMemoryUserRepository)

**Позитивные сценарии конкурентности**
Общая схема:
1. Запуск множества одновременных параллельных потоков/задач над общим экземпляром InMemoryUserRepository
2. Проверка целостности данных, корректности размера коллекции и отсутствия исключений

Тест-кейсы:
1. Параллельное добавление уникальных пользователей:
   - [ ] 100 одновременных вызовов Add с уникальными UserId -> в хранилище ровно 100 пользователей, GetAll возвращает 100 элементов без потерь, отсутствие исключений
2. Параллельный Add одного и того же пользователя:
   - [ ] 50 потоков одновременно вызывают Add с одним и тем же UserId -> возвращается валидный User, дубликаты не появляются, отсутствие исключений
3. Параллельное обновление одного и того же пользователя:
   - [ ] 100 одновременных потоков вызывают Update для одного существующего UserId -> все вызовы завершаются успешно (возвращают true), исключения отсутствуют, конечное состояние пользователя валидно
4. Одновременное чтение и запись:
   - [ ] 50 потоков непрерывно читают (GetAll, GetById), пока 50 потоков параллельно добавляют и обновляют пользователей -> операции чтения и записи не выбрасывают исключений, снимок коллекции и целостность данных сохраняются

## Глобальная обработка ошибок

**Негативный сценарий сбоя сервера**
Общая схема:
1. Подмена зависимости (мокирование IUserRepository или IUserService с выбросом new Exception("Database critical disaster")) в тестовой WebApplicationFactory
2. Отправка HTTP-запроса к API
3. Middleware перехватывает ошибку и логирует ее
4. Возвращается чистый JSON со статусом 500 Internal Server Error в формате ProblemDetails без утечки stack trace

Тест-кейсы:
1. Непредвиденный сбой в пайплайне:
   - [ ] Мокирование IUserRepository или IUserService с выбросом new Exception("Database critical disaster") в WebApplicationFactory -> ответ 500 Internal Server Error, JSON-структура ProblemDetails ({"status": 500, "detail": "Ошибка сервера, попробуйте позже!"}), полное отсутствие stack trace и внутренних деталей исключения в теле ответа
